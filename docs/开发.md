可以，而且你既然准备重写，**最佳方案不是把现有 FastAPI+SQLite 生硬搬上云，而是做一套真正的云原生版本，同时最大化复用现有 Vue 页面、业务模型和测试逻辑。**

## 最终推荐技术栈

```text
GitHub
  └─ 源码、PR、CI/CD

Vercel
  ├─ Vue 3 前端静态站点
  ├─ TypeScript Serverless Functions
  └─ AI 调用、敏感业务接口

Supabase
  ├─ Auth 用户登录
  ├─ PostgreSQL 数据库
  ├─ Storage 私有图片存储
  └─ Row Level Security 数据隔离
```

我最推荐的是：

> **Vue 3 + TypeScript + Vite + Pinia + TanStack Query + Supabase + Vercel TypeScript Functions + Vercel AI SDK Core。**

而不是继续把整个 FastAPI 后端部署到 Vercel。

# 一、为什么推荐全栈 TypeScript

你现有前端已经是：

- Vue 3；
- Vite；
- Vue Router；
- Pinia；
- Axios。

这些页面、组件、日历、适老化样式可以大量复用。

现有后端是：

- FastAPI；
- Pydantic；
- HTTPX；
- Pillow；
- Keyring；
- 本地文件和SQLite逻辑。

Vercel目前可以运行FastAPI，但其Python Runtime仍标为Beta；FastAPI应用会整体成为一个Vercel Function。([Vercel][1])

既然你已经决定重写，改成TypeScript后会有几个好处：

- 前后端使用同一种语言；
- 数据类型和校验规则可以共享；
- Supabase官方JS SDK集成最自然；
- Vercel的Node/TypeScript生态更成熟；
- AI SDK、流式响应、结构化输出更方便；
- 不再维护Python、Node两套依赖和构建环境；
- 不再需要Uvicorn、Keyring、PyInstaller、本地进程等桌面逻辑。

**Mac桌面版继续保留现有FastAPI代码；云端版单独用TypeScript重写。**

## 核心框架


继续Vue 3能最大化复用现有代码。

```text
Pinia
└─ 登录状态、当前投研日期、字体大小、UI偏好
```

```ts
export const analysisResultSchema = z.object({
```

现有Pydantic输出结构可以直接转成Zod结构，业务设计不需要重新想。

- 服务端生成签名地址；
- 跨用户操作；
- 复杂审计。

Vercel Functions会自动扩缩容，并适合调用数据库和外部AI这类I/O密集任务。([Vercel][2])

## AI部分

推荐：

```text

```

Vercel AI SDK Core支持多模型统一调用和结构化输出，可以通过Schema约束模型结果，减少当前手工解析JSON的问题。([Vercel][3])

```ts
interface AnalysisProvider {

class OpenAIProvider implements AnalysisProvider {}
class VolcengineProvider implements AnalysisProvider {}
class AnthropicProvider implements AnalysisProvider {}
```

第一版实现一个实际使用的Provider，但接口提前保留。



绝对不能放到Vue的`VITE_*`环境变量里，因为`VITE_*`会进入浏览器代码。

# 四、Supabase具体负责什么

## 1. Supabase Auth

建议做成**邀请制单用户/少用户系统**：

```text
管理员创建账号
→ 李叔使用邮箱或用户名密码登录
→ 长期保持登录
```

不建议第一版开放任何人注册。

Supabase Auth使用JWT，并能和PostgreSQL的RLS结合，让每个用户只能访问自己的数据。([Supabase][4])

对于李叔，登录页尽量简单：

```text
账号
密码
[登录]
☑ 保持登录
```

不要默认使用邮箱魔法链接，因为老人还要来回打开邮箱。

## 2. Supabase PostgreSQL

SQLite中的业务模型可以大部分照搬，但每张用户数据表都要加：

```sql
user_id uuid not null references auth.users(id)
```

建议核心表：

```text
profiles
module_definitions
module_entries
assets
entry_assets
combinations
combination_modules
analyses
analysis_inputs
analysis_input_assets
audit_logs
user_settings
```

### 核心日期模块表

```sql
create table module_entries (
    id uuid primary key default gen_random_uuid(),
    user_id uuid not null references auth.users(id),
    module_id smallint not null,
    record_date date not null,

    display_title text not null default '',
    text_content text not null default '',

    status text not null default 'draft',
    revision integer not null default 1,

    period_start date,
    period_end date,

    created_at timestamptz not null default now(),
    updated_at timestamptz not null default now(),

    unique (user_id, record_date, module_id)
);
```

这和现有的“投研日期+12模块”模型完全一致。

## 3. Row Level Security

所有公开Schema中的用户表必须启用RLS。Supabase官方明确要求，暴露给Data API的表必须启用RLS；Service Role能够绕过RLS，因此绝不能出现在浏览器中。([Supabase][5])

通用策略：

```sql
alter table module_entries enable row level security;

create policy "用户只能读取自己的模块"
on module_entries
for select
using (auth.uid() = user_id);

create policy "用户只能创建自己的模块"
on module_entries
for insert
with check (auth.uid() = user_id);

create policy "用户只能修改自己的模块"
on module_entries
for update
using (auth.uid() = user_id)
with check (auth.uid() = user_id);

create policy "用户只能删除自己的模块"
on module_entries
for delete
using (auth.uid() = user_id);
```

即使有人拿到了前端的Supabase Publishable Key，也无法读取李叔的数据。

# 五、图片存储

## 使用Supabase Storage私有Bucket

建立：

```text
stock-helper-assets
```

设置为Private。

文件路径统一：

```text
{user_id}/{record_date}/{module_id}/{uuid}.webp
```

例如：

```text
8fb7.../2026-08-04/7/550e8400.webp
```

Supabase Storage支持私有文件、RLS访问控制和图片处理。([Supabase][6])

## 上传不要经过Vercel Function

正确流程：

```text
浏览器压缩图片
→ 直接上传Supabase Storage
→ 数据库写入assets元数据
→ 创建entry_assets关联
```

这样避免：

```text
浏览器
→ Vercel
→ Supabase
```

双重传输。

## 图片应保存两种版本

```text
original
└─ 用户原图

ai_ready
└─ 最长边1600或2048像素
```

AI分析只使用`ai_ready`，原图用于查看和历史留存。

数据库保存：

```text
id
user_id
storage_path
ai_storage_path
original_name
mime_type
file_size
width
height
sha256
created_at
```

需要显示图片时：

- 浏览器携带登录凭据读取私有对象；
- 或服务端生成短时间签名URL。

Supabase支持生成有期限的签名访问地址。([Supabase][7])

# 六、AI分析的最佳流程

不要在前端直接调用AI，也不要依赖Vercel实例内存保存任务。

## 第一步：创建分析快照

```text
POST /api/analyses
```

Vercel Function执行：

```text
验证Supabase JWT
→ 验证user_id
→ 查询选中的模块
→ 固化文字和图片快照
→ 创建analyses记录
→ 状态设为running
```

## 第二步：调用AI

```text
获取私有图片
→ 构建有序多模态消息
→ 调用模型
→ 使用Zod验证结构化结果
→ 保存原始输出和标准化结果
```

## 第三步：保存结果

```text
status = completed
raw_result
normalized_result
completed_at
provider
model
token_usage
```

失败：

```text
status = failed
error_code
safe_error_message
```

## 前端处理

```text
提交分析
→ 获得analysis_id
→ 显示“正在分析”
→ 轮询数据库状态
→ 完成后进入结果页
```

第一版可以让函数同步完成调用，但必须先把任务记录写入数据库。这样即使浏览器断开，也能判断任务究竟成功还是失败。

# 七、不建议同时使用Supabase Edge Functions

第一版不要同时引入：

```text
Vercel Functions
+
Supabase Edge Functions
```

两套Serverless后端会导致：

- 日志分散；
- 密钥重复配置；
- 部署流程复杂；
- 本地调试复杂；
- 责任边界不清。

建议第一版统一：

```text
页面和API：Vercel
数据、登录、图片：Supabase
```

后期只有数据库触发任务、定时清理或特别靠近数据库的逻辑，才考虑Supabase Edge Functions。
